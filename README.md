# Ранжирование регулирующих НПА по тексту таможенной декларации

Для каждой из 151 декларации решение возвращает 10 наиболее подходящих позиций контрольных
списков (562 позиции из указов № 1661, 202, 36, 1005, 1082, 1083 и решения КЕЭК № 30)
в порядке убывания релевантности — `out/predictions.csv`.

Кратко о подходе: **гибридный поиск из семи ранжированных списков — BM25 по леммам, TF-IDF по
символьным n-граммам и два dense-энкодера (USER-bge-m3, ru-en-RoSBERTa), каждый с двумя
запросами — слитых Reciprocal Rank Fusion**. Позиции списка 1661 дополнены названием категории
(«вычислительная техника», «электроника»…). Переранжирование кросс-энкодером реализовано, но по
умолчанию выключено: на dev-разметке оно не улучшает сильный гибрид, а стоит 4,5 мин на GPU.
Все модели локальные, сетевых запросов во время запуска нет. Прогон: 2 мин на GTX 1650 SUPER
(2,7 ГБ RAM), на слабом 4-ядерном CPU 2011 года — 20 мин с тем же результатом.

## 1. Установка, запуск, воспроизводимость

Требования: Python 3.10, ~4 ГБ на диске под модели, GPU опционально.

```bash
pip install -r requirements.txt      # версии зафиксированы
python prepare.py                    # однократно, с сетью: модели → ./models (+ индекс ТН ВЭД → ./data)
python run.py --out ./out            # запуск без сети: ./out/predictions.csv
```

`prepare.py` скачивает (или копирует из локального кэша HF) три модели с зафиксированными
ревизиями и пишет `models/MANIFEST.json` (реранкер нужен только для `--rerank`):

| модель | параметров | назначение | ревизия |
|---|---|---|---|
| `deepvk/USER-bge-m3` | 568M | dense-эмбеддинги (русскоязычная дообученная bge-m3) | `0cc6cfe4` |
| `ai-forever/ru-en-RoSBERTa` | 404M | второй dense-энкодер (другая архитектура — другие ошибки) | `89fb1651` |
| `BAAI/bge-reranker-v2-m3` | 568M | кросс-энкодер для переранжирования (опция `--rerank`) | `953dc6f6` |

`run.py` до импорта `transformers` выставляет `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`
и загружает модели только из `./models` (если их нет — завершается с кодом 2 и подсказкой).

Полезные флаги `run.py`:

| флаг | по умолчанию | смысл |
|---|---|---|
| `--device auto\|cpu\|cuda` | `auto` | устройство |
| `--rerank` | выкл. | переранжирование top-K кросс-энкодером (§4.4) |
| `--rerank-k N` | 20 | глубина переранжирования |
| `--time-budget S` | 1500 | общий бюджет времени: второй энкодер и реранкер отключаются, если не укладываются |
| `--no-second-encoder` | | без RoSBERTa (абляция) |
| `--tnved` | выкл. | ТН ВЭД-обогащение запроса (см. §5.3 — на dev ухудшает) |
| `--fp16` | выкл. | fp16 на GPU; быстрее только с тензорными ядрами (см. §7) |
| `--lam`, `--w-tnved`, `--seed` | 0.1, 0.5, 42 | параметры слияния |

Проверка формата и тесты: `python -m pytest -q` (21 тест: валидатор CSV, препроцессинг,
BM25/RRF, разрешение ссылок, бюджет реранкера). Оценка на ручной dev-разметке:
`python evaluate.py`.

Результат: `out/predictions.csv` — колонки `declaration_id, rank, regulation_id, score`;
ровно 10 уникальных `regulation_id` с рангами 1–10 на декларацию; `score` конечный и
не возрастает с рангом. Формат проверяется валидатором перед записью
(`src/io_utils.validate_predictions`). Дополнительно пишется `out/debug_rankings.jsonl`
с top-50 каждой стадии — для анализа ошибок.

### 1.1 Время, память, воспроизводимость

Замеры на i5-2500K (4 ядра, 2011 г., без AVX2), 8 ГБ RAM, GTX 1650 SUPER 4 ГБ, WSL2:

| режим | время | RSS | примечание |
|---|---|---|---|
| GPU (fp32), по умолчанию | 1 мин 57 с | 2.7 ГБ | эмбеддинги bge-m3 31 с, RoSBERTa 50 с, BM25 + n-граммы + RRF 3 с |
| CPU (4 потока), по умолчанию | 19 мин 51 с | 4.0 ГБ | эмбеддинги 603 с + 573 с; порядок совпадает с GPU в 1505 из 1510 строк (2 декларации, перестановки соседних позиций из-за fp32-арифметики) |
| GPU, `--rerank` | 6 мин 27 с | 3.5 ГБ | + 3020 пар кросс-энкодера (~11 пар/с) |

На CPU время почти целиком уходит на два энкодера; на современном CPU (8+ ядер, AVX-512)
ожидаемо в 4–6 раз быстрее. Защита лимита: если после первого энкодера прогноз «×2 + 60 с»
не укладывается в `--time-budget` (25 мин), второй энкодер пропускается с предупреждением
(результат — RRF из 5 списков); реранкер при `--rerank` работает раундами по глубине и откатывает
незавершённый раунд (§4.4). Пик VRAM 2.3 ГБ; энкодеры выгружаются последовательно.

Сданный `out/predictions.csv` получен на GPU. Воспроизводимость: `requirements.txt` с точными
версиями; ревизии моделей зафиксированы в `prepare.py` и `models/MANIFEST.json`; seed фиксирован;
два прогона на GPU дают побайтно одинаковый файл (проверено `md5sum`); оффлайн-режим проверен
запуском с недоступной сетью (`unshare -rn`) и пустым `HF_HOME`.

Версии: Python 3.10.12, torch 2.2.1 (cu121), transformers 4.46.0, sentence-transformers 3.2.1,
scikit-learn 1.4.1, numpy 1.26.4, pandas 1.5.2, pymorphy3 2.0.6.

## 3. Данные: что важно для решения

**Декларации.** Из служебных полей полезно только `G31_1` — описание товара. Остальные поля
константны или пусты (`G011="ИМ"`, `GD0="10"`, `has_acceptance_docs=0`, `G33` с кодом ТН ВЭД
отсутствует). Текст шумный: верхний регистр, разорванные слова («Т ВЕРДОТЕЛЬНЫХ», «КАРО ТАЖА»),
маскированные номера («5XXXXX7»), англоязычные вставки, длина от 48 до 2131 символов, часто
несколько товаров в одной декларации, повторы.

**НПА.** 562 позиции контрольных списков экспортного контроля. 350 — из указа № 1661 (список
двойного назначения) с префиксом «Раздел N, x.y.z.»; у остальных указов номера пунктов в тексте
нет. 220 позиций ссылаются на другие пункты («компоненты для изделий, указанных в пункте
6.1.4.4.2») — сами по себе они почти пусты. Текст позиции — не описание товара, а *условие
контроля*: пороги, оговорки, «имеющие любую из следующих характеристик».

## 4. Подход

### 4.1 Препроцессинг (`src/preprocess.py`)

* нижний регистр, `ё→е`, удаление маскированных номеров (`\S*[xх]{3,}\S*`);
* склейка разорванных слов по словарю pymorphy3: «т вердотельных» → «твердотельных»,
  «каро тажа» → «каротажа» (склеиваем, если кусок неизвестен словарю, а склейка известна);
* для BM25 — леммы pymorphy3 без стоп-слов; дефисные составные режутся на части
  («молекулярно-эпитаксиальный» → «молекулярно», «эпитаксиальный»), иначе запрос
  «эпитаксиальная установка» не находит позицию «оборудование для молекулярно-эпитаксиального
  выращивания» (реальная ошибка первой версии);
* для нейросетей — та же нормализация без лемматизации. **Нижний регистр обязателен:**
  токенизатор XLM-R режет «ТВЕРДОТЕЛЬНЫХ НАКОПИТЕЛЕЙ» на 12 бессмысленных кусков против
  4 токенов в нижнем регистре, и dense-поиск на исходном тексте деградирует.

### 4.2 Документы НПА (`src/corpus.py`)

* из текста выделяется номер пункта (для 1661) и «тело» позиции;
* **разрешение ссылок**: по регулярке извлекаются номера пунктов («в пункте 6.1.6.1, 6.1.6.2
  или 6.1.6.3», «подпункте "а" пункта 6.1.4.4.2», «позициях 9.1.3 или 9.1.5»), и если целевой
  пункт того же указа есть в выборке, его текст (до 300 символов) дописывается в документ.
  Разрешено 69 ссылок из 354: остальные ведут на пункты вне выборки или в указы без номеров
  пунктов в тексте (допущение зафиксировано);
* **категория списка 1661**: разделы 1–3 указа нумеруются по девяти категориям (1 — специальные
  материалы, 2 — обработка материалов, 3 — электроника, 4 — вычислительная техника, 5 —
  телекоммуникации и защита информации, 6 — датчики и лазеры, 7 — навигация, 8 — морская техника,
  9 — двигательные установки и космос); по первой цифре пункта позиция получает короткий заголовок
  «вычислительная техника: эвм и сопутствующее оборудование…». Это переводит позицию на «товарный»
  язык; длинное название указа, напротив, размывало эмбеддинг (§5.2). Разделы 4–5 устроены иначе,
  категории им не приписываются;
* документ для BM25 = категория + тело + тексты ссылок; для dense — категория + тело; для
  символьных n-грамм и реранкера — тело + ссылки.

### 4.3 Поиск кандидатов (`src/retrieval.py`)

* **BM25** (k1=1.2, b=0.75, собственная реализация ~40 строк) по леммам — ловит точные
  термины и аббревиатуры (`uf6`, `pav`, «тиристорный»);
* **TF-IDF по символьным n-граммам** (3–5 символов внутри слов, `char_wb`, sublinear tf) — второй
  лексический сигнал, устойчивый к опечаткам и склейкам, которых в декларациях много
  («СОЭДАНИЯ», «МАРТИЦА», «ЭЛЕКТРОHHЫЕ» с латинскими H, «КАЧЕСТВЕКОМПЛЕКТУЮЩЕГО»); BM25 по
  леммам их не видит. Два запроса: полный текст и «голова». Кроме того, он возвращает вес
  лексике: после добавления второго энкодера четыре dense-списка перевешивали один BM25;
* **dense**: USER-bge-m3, CLS-пулинг, косинус. Два запроса на декларацию: полный текст и
  «голова» — первые 250 символов. Название товара почти всегда в начале, а хвост
  (серийные номера, ТУ, состав комплекта) — шум, который размывает эмбеддинг;
* **второй dense**: ru-en-RoSBERTa (RoBERTa-архитектура против XLM-R у bge-m3, обучена на
  других данных, с префиксами `search_query:` / `search_document:`), те же два запроса. Сам по
  себе он слабее bge-m3, но ошибается на других декларациях, и в слиянии поднимает recall
  кандидатов на 6 п.п. (§5.2);
* **слияние**: Reciprocal Rank Fusion (k=60) семи списков — BM25, n-граммы(полный),
  n-граммы(голова), bge(полный), bge(голова), RoSBERTa(полный), RoSBERTa(голова) с равными
  весами. Итоговый `score` — нормированный по top-20 RRF-score в [0, 1] (1 у первого кандидата; не вероятность, только порядок). RRF выбран вместо взвешенной суммы score, потому что шкалы BM25 и косинуса
  несопоставимы, а рангов — достаточно; настраивать веса на 31 размеченной декларации —
  переобучение.

### 4.4 Переранжирование (`src/rerank.py`, опция `--rerank`)

По умолчанию выключено. История: пока гибрид состоял из трёх списков (nDCG 0.631 на dev),
реранкер давал +0.05; после добавления второго энкодера, n-грамм и категорий (0.746) он не
добавляет ничего (0.716–0.744 в зависимости от λ), а стоит 4,5 мин на GPU и делает результат
зависимым от железа. Реализация оставлена и проверяется: `python run.py --out ./out --rerank`.

Top-20 кандидатов оценивает кросс-энкодер bge-reranker-v2-m3 парой (голова декларации,
текст позиции + ссылки). Итоговый `score = (sigmoid(logit) + 0.1 · hybrid_norm) / 1.1`, где
`hybrid_norm` — нормированный RRF-score кандидата: он разрывает ничьи и удерживает порядок при
близких логитах. Score лежит в (0, 1], но это не калиброванная вероятность — только порядок.
Не переранжированные кандидаты (если сработал бюджет) получают score ниже любого
переранжированного и сохраняют гибридный порядок.

**Почему запрос — «голова», а не весь текст.** У кросс-энкодера окно 512 токенов и усечение
`longest_first`: при декларации в 2000 символов усекается *документ*, и модель сравнивает
запрос с обрубком позиции. С головой в 250 символов реранкер даёт nDCG 0.671 против 0.590
с полным запросом (при одинаковой глубине 40, табл. в §5.2) — это самый большой единичный
прирост в работе.

**Бюджет времени.** Кандидаты обрабатываются раундами по глубине (позиции 1–10 у всех
деклараций, затем 11–20, …). Если бюджет (`--time-budget`, по умолчанию 25 мин с учётом уже
прошедшего времени) исчерпан посреди раунда, раунд откатывается, остаются только завершённые.
Так качество на слабом CPU деградирует равномерно по всем декларациям, а результат при любой
завершённой глубине детерминирован. Чтобы не тратить время на заведомо незавершаемый раунд, после
5 деклараций раунда его длительность экстраполируется, и раунд прерывается сразу, если прогноз
не укладывается в остаток бюджета. На GPU оба раунда (3020 пар) занимают ~4,5 мин.

## 5. Проверка решений и эксперименты

### 5.1 Dev-разметка

Правильных ответов в комплекте нет, поэтому для сравнения конфигураций сделана ручная разметка
31 декларации (`data/dev_labels.jsonl`, 100 пар): стратифицированно по типам товаров (СХД и
серверы, микросхемы, тиристоры, вакуумные насосы, нейтронные трубки, криостат, станки,
подшипники, связь, криптография, огнетушители, стандарты частоты…). Оценки: 2 — позиция
описывает именно этот товар (без проверки порогов), 1 — частичное/возможное соответствие.
Разметка делалась по объединению top-12 всех стадий плюс поиск по ключевым словам во всём
списке, чтобы находить и то, чего поиск не нашёл (так найдены 4 из 6 «пропусков» ниже).

Ограничения разметки: это суждение автора, не эталон организаторов; выборка мала, поэтому
различия в сотые доли nDCG — шум; разметка смещена в сторону того, что вообще нашлось
(recall переоценён). Использована только для *относительного* сравнения вариантов.

| название товара шестым списком в RRF | 0.677 | 0.775 | 0.720 | 0.833 | 0.484 |
| то же, K = 30 / 40 / 60 | 0.672 / 0.671 / 0.662 | 0.748 / 0.738 / 0.720 | 0.723 / 0.739 / 0.755 | | |
| то же, λ = 0 / 0.3 / 1.0 | 0.618 / 0.689 / 0.654 | 0.691 / 0.805 / 0.766 | 0.692 / 0.706 / 0.706 | | |
| то же, голова 150 / 400 | 0.667 / 0.639 | 0.755 / 0.741 | | | |

Веса слияния: `bm25 ×2` (0.693) и BM25 по «голове» (0.698) на 5 списках подтверждают, что
лексический сигнал был разбавлен, но n-граммы решают это лучше (0.720); `rrf_k` 20/100 — хуже 60;
RoSBERTa с весом 0.5 — не лучше 1.0. Для реранкера: глубина K=20/30/40 не различается,
чистый реранкер (λ=0) хуже смеси.

Выводы, которые определили итоговую конфигурацию:

1. **Гибрид сильно лучше любого одиночного метода** (0.631 vs 0.49/0.52): BM25 и dense
   ошибаются на разных декларациях — пересечение их top-10 по всем 151 декларациям всего 26 %.
2. **Название списка в тексте документа вредит** и dense (0.417 → 0.520), и реранкеру: позиция
   «вакуумные насосы > 5 м³/ч» с префиксом «…для создания химического оружия» опускалась
   реранкером с 1-го на 16-е место для обычного диффузионного насоса.
3. **Короткий запрос лучше полного** и для dense, и особенно для реранкера (см. §4.4).
4. **Реранкер полезен только с коротким запросом**; с полным он ухудшает гибрид.
5. **ТН ВЭД-обогащение ухудшает** — см. §5.3.
6. **Второй энкодер поднимает recall** (0.682 → 0.743): методы с разной архитектурой ошибаются
   в разных местах, и RRF это использует.
7. **Символьные n-граммы — самый большой прирост после гибридизации** (0.651 → 0.720): опечатки
   и склейки в декларациях + возврат веса лексике при четырёх dense-списках.
8. **Категории 1661 работают** (+0.02–0.03) как короткий «товарный» заголовок — в отличие от
   длинного названия указа, которое вредило.
9. **Реранкер стал лишним.** На слабом гибриде он давал +0.05, на сильном — 0 (или минус при
   малом λ). На 31 примере это «не хуже и не лучше»; выключен ради времени и воспроизводимости
   на CPU, оставлен как опция.
10. **Название товара как отдельный запрос не помогает.** Выделение наименования (первый сегмент
   до `:`/`;`/точки, с пропуском служебных преамбул «5.2 имущество по перечню…») и как шестой
   список в RRF, и как запрос реранкера даёт ±1 декларацию из 31 — «голова 250» уже покрывает
   то же самое. Не внедрено.

### 5.3 ТН ВЭД: рассмотрено и отвергнуто (для текущих данных)

К заданию приложен дамп справочника ТН ВЭД (`tnved_knowledge.txt`, 13 145 листовых кодов с
нормализованными названиями). Кодов ТН ВЭД нет ни в декларациях (графа 33 вырезана), ни в
позициях НПА (проверено регуляркой по всем 562 текстам), поэтому напрямую связать их нельзя.

Была реализована и проверена гипотеза «семантического моста» (`src/tnved.py`, флаг `--tnved`):
описание товара → 5 ближайших позиций ТН ВЭД (BM25 + dense) → их нормализованные названия
(«Оборудование холодильное или морозильное прочее») как дополнительный запрос к НПА, со своим
весом в RRF. На dev это ухудшило все метрики (0.631 → 0.549). Причина — ошибки самой
классификации по коду: «нейтронные трубки» уходили в «трубы бурильные», «устройство сетевой
безопасности Cisco ASA» — в «устройства для защиты электрических цепей», «тиристорные модули» —
в «модули с плоской дисплейной панелью». Шум расширения перевешивал пользу нормализации.
Код оставлен как задокументированный отрицательный результат; по умолчанию выключен. Вывод для
целевой архитектуры (§8): справочник надо применять на стороне *документов* (у позиции коды известны
точно), а не на стороне запроса, где код приходится угадывать.

### 5.4 Согласованность методов (все 151 декларации)

Для каждой декларации берётся доля общих позиций в двух top-10, затем среднее по 151 декларации.

| пара методов | доля общих позиций в top-10 |
|---|---|
| BM25 ~ bge-m3 | 0.24 |
| BM25 ~ гибрид | 0.44 |
| bge-m3 ~ гибрид | 0.50 |
| гибрид ~ итог | 1.00 (реранкер выключен) |

Гибрид равноудалён от BM25 и bge-m3: три лексических списка (BM25 + два n-граммных) против
четырёх dense (два энкодера × два запроса). С включённым реранкером (`--rerank`) итог совпадает с
гибридом на ~84 % — реранкер переставляет внутри top-10, а не находит новое: recall определяется
первой стадией.

## 6. Сложности, анализ ошибок и как они учтены

1. **Разрыв словарей «товар ↔ условие контроля».** Декларация описывает товар («СЕРВЕР POWEREDGE
   MX7000»), позиция — условие («ЭВМ и сопутствующее оборудование, специально разработанные,
   чтобы отвечать любому из условий…»). Пропуски на dev именно такие: `NPA0420` (ЭВМ) для
   сервера, `NPA0048` (криптография цифровыми методами) для межсетевого экрана с 3DES/AES,
   `NPA0404` (силовые полупроводниковые модули) для тиристорного модуля, `NPA0551`
   (радионавигационные приёмники с шифрованием) для ГНСС-указателя курса — ни BM25 (ранг 69–552),
   ни dense не вытаскивают их в top-20. Частично закрывается dense-моделью и коротким запросом;
   полностью — обогащением позиций названиями их кодов и примерами деклараций (§8) или дообучением
   на реальных парах.
2. **Пороги не проверяются.** Позиция «вакуумные насосы производительностью более 5 м³/ч»
   и насос на 40 м³/ч совпадают, но текстовые модели не сравнивают числа: они ставят позицию
   высоко и для насоса на 2 м³/ч. «Релевантность» в решении определена как «товар относится
   к классу, описанному в позиции»; проверка порогов — отдельный шаг (LLM-судья или правила),
   отвергнутый по бюджету времени (§7).
3. **Пункты-ссылки без собственного содержания** (220 из 562). Разрешение ссылок внутри указа
   помогло для 69 ссылок; для остальных целевые пункты отсутствуют в выборке — такие позиции
   остаются «слепыми» для любого текстового метода.
4. **Шум декларации**: разорванные слова и маски исправляются на препроцессинге; хвост из
   серийных номеров и ТУ нейтрализуется «головой» запроса. Остаются опечатки-склейки без
   пробела («КАЧЕСТВЕКОМПЛЕКТУЮЩЕГО») и латиница внутри кириллицы («ТРАНЗИСТОР 2T828A»).
5. **Одинаковые позиции в разных указах и разделах** (например, 1661 разделы 1/2/3 содержат
   почти идентичные пункты 6.1.1.1.2.3; 1082 содержит две почти одинаковые позиции про насосы).
   Они занимают несколько мест в top-10 — это правильно, если разметка организаторов включает
   обе, и «расточительно» иначе. Дедупликация не делалась: без эталона нельзя выбрать одну.
6. **Прайор указа 1661** (62 % корпуса) воспроизводится в ответах (62 % в top-10) — модель не
   искажает распределение; при этом для 24 деклараций top-1 из КЕЭК № 30 (базовые станции,
   огнетушители с галоном, интегральные схемы с шифрованием) — короткие «товарные» позиции
   этого списка матчатся хорошо.
7. **Многотоварные декларации** («в составе: 1)… 5)…») получают ответ по первому/доминирующему
   товару; остальные компоненты попадают в top-10 только если проходят гибрид.
8. **Уверенность.** Итоговый score — нормированный RRF, он показывает согласие списков, а не
   вероятность. Для гражданских товаров без явной контрольной позиции (гребные валы для
   гражданских судов, запчасти КАМАЗ, принтеры) списки расходятся, и top-10 собирается из
   слабых совпадений. Такие декларации — главный источник ошибок ранжирования по любой метрике.
   Пример цены n-грамм: для промышленного принтера позиция КЕЭК № 30 «Принтеры, копировальные
   аппараты…» — top-1 у bge-m3, но 4-е место в итоге: короткая позиция проигрывает по
   символьным n-граммам длинным текстам про «машины».
9. **Две декларации содержат явную ссылку** «КОД СПИСКА – 04, ПОЗИЦИЯ СПИСКА – 12.1.1»:
   в проде это парсится напрямую; в выборке пункта 12.1.1 нет, поэтому не использовалось.

## 7. Рассмотренные альтернативы

| вариант | решение |
|---|---|
| Только BM25 / только dense | хуже гибрида на 0.2+ nDCG (§5.2) |
| Взвешенная сумма score вместо RRF | несопоставимые шкалы, лишние гиперпараметры на 31 примере |
| Кросс-энкодер bge-reranker-v2-m3 поверх гибрида | реализован (`--rerank`); на итоговом гибриде не даёт прироста на dev, выключен (§4.4) |
| LLM-судья (Qwen3-4B/1.7B) поверх top-20 с проверкой порогов | самый перспективный шаг для precision, но 151×20 промптов по ~600 токенов на GTX 1650 SUPER — на границе 30 мин, на CPU нереально; не входит в решение |
| Генеративное переписывание запроса LLM | тот же бюджет; частично заменяется «головой» запроса |
| Qwen3-Reranker-0.6B вместо bge-reranker | не проверялся: bge-reranker-v2-m3 уже в кэше и уложился по времени; Qwen3-Reranker-4B в fp16 не помещается в 4 ГБ VRAM |
| Дедупликация одинаковых позиций в top-10 | без эталона нельзя выбрать «правильный» дубль |
| ТН ВЭД-обогащение запроса | реализовано, ухудшает (§5.3) |
| fp16 на GPU | на GTX 16xx (без тензорных ядер) fp16 в 8 раз медленнее fp32 (0.5 vs 4 TFLOPS в matmul) — первый прогон реранкера занял бы 45 мин; по умолчанию fp32, `--fp16` для GPU с тензорными ядрами |

## 8. Целевая архитектура: обогащение позиций НПА через коды ТН ВЭД

Текстовое сопоставление — то, что можно сделать на выданных данных, и его главная слабость —
разрыв словарей: декларация описывает *товар*, позиция списка — *условие контроля* (§6, п. 1).
Целевое решение закрывает этот разрыв не на стороне декларации, а на стороне документов:
позиции НПА обогащаются текстами, написанными языком деклараций. Сама декларация остаётся как
есть — код ТН ВЭД для неё не нужен и не определяется. Пайплайн (BM25 + dense → RRF → реранкер)
не меняется, меняется только то, что лежит в индексе.

**Как устроены контрольные списки.** В первоисточниках каждой позиции соответствует не только
описание, но и коды ТН ВЭД (одна или несколько строк вида «из 8418 69 000 8»; на alta.ru акты
опубликованы таблицей «пункт | наименование | код»: `2.2.1.1 | Токарные станки… | 8458;
8464 90 000 0; 8465 20 000 0`). Например, у пункта 6.1.2.4.1 указа 1661 («криогенные охладители,
пригодные для применения в космосе») — код 8418 69 000 8. В `regulations.json` колонка с кодами
вырезана; это ключ, который связывает позицию с миром товаров.

**Три слоя обогащения позиции:**

```
позиция НПА ──► коды ТН ВЭД (из первоисточника акта)
                   │
                   ├──► названия кодов из tnved_knowledge.txt
                   │      «Оборудование холодильное или морозильное прочее»
                   │
                   └──► примеры декларирования по коду (ifcg.ru/kb/tnved/<код>/)
                          «ЛАБОРАТОРНОЕ ХОЛОДИЛЬНОЕ ОБОРУДОВАНИЕ, ОХЛАЖДАЮЩИЙ/НАГРЕВАЮЩИЙ
                           ТЕРМОСТАТ; CIRCULATION THERMOSTAT F25-MA…»

документ позиции = текст условия контроля + названия кодов + примеры деклараций
```

1. *Позиция → коды.* Парсинг семи актов (сноски, «из», перечисления, диапазоны) и привязка
   к 562 позициям: по «раздел + номер пункта» для 1661, по тексту — для остальных; таблица
   переходов между версиями ТН ВЭД (дамп 2022 года, акты редактировались 2011–2024).
   Оценка — около одного рабочего дня.
2. *Коды → названия.* Прямо из `tnved_knowledge.txt` (13 145 листовых кодов с нормализованными
   названиями; для 4–6-значных кодов в актах — названия узлов дерева). Это переводит позицию
   на «товарный» язык: «сервер» находит «машины вычислительные», а не только «ЭВМ, отвечающие
   условиям…».
3. *Коды → примеры деклараций.* База [ifcg.ru/kb/tnved](https://www.ifcg.ru/kb/tnved/) даёт на
   каждый код 10–15 обезличенных описаний товаров из реальных деклараций — в том же формате,
   что наша `G31_1`. Это самое сильное обогащение: в индексе появляются тексты, *неотличимые от
   запроса*, и матчинг «декларация ↔ декларация» работает и для BM25, и для dense-модели без
   какого-либо переноса между стилями. Примеров много, поэтому хранить их надо не одним слитым
   текстом (размоется), а как отдельные псевдодокументы позиции: каждый пример — свой эмбеддинг,
   позиция получает максимум сходства по своим примерам, дальше RRF как сейчас.

**Что остаётся текстовому реранкеру.** Обогащение поднимает recall: у позиции появляются
слова, которыми товар описывают декларанты. Но «из 8418 69» — это и промышленные холодильники,
и космические криокулеры, а код 8542 стоит в дюжине пунктов 1661. Разводить позиции с одинаковыми
кодами и отсеивать товары, не проходящие по условию контроля, должен кросс-энкодер
«декларация ↔ текст условия». В текущем решении он реализован, но выключен: на выданных данных
он не улучшает гибрид (§4.4). В целевой архитектуре у него появляется то, чего сейчас нет, —
обучающие пары: поле `has_acceptance_docs` (декларации, к которым прилагались разрешительные
документы) даёт реальные примеры «описание → пункт списка» для дообучения, и именно дообученный
реранкер, а не готовый, становится второй стадией.

**Почему не в этом решении.** Условие требует решения на выданных файлах; сбор двух внешних
таблиц («позиция → коды» из актов, «код → примеры» с ifcg.ru) — отдельная работа на несколько
дней с парсингом и ручной сверкой. Здесь внешние данные сознательно не использовались;
описанное выше — план следующего шага, который не требует переделки пайплайна.

## 9. Допущения

* Ground truth отсутствует; «релевантность» = «декларируемый товар относится к классу товаров,
  описанному в позиции», без проверки числовых порогов.
* Ссылки между пунктами разрешаются только внутри указа 1661 и только на пункты из выборки.
* На каждую декларацию возвращаются 10 позиций даже если, по мнению модели, товар не подпадает
  ни под одну (формат требует ровно 10); `score` при этом низкий.
* При нехватке времени на CPU пропускается второй энкодер (и раунды реранкера при `--rerank`);
  формат и детерминизм при этом сохраняются.
* Входные файлы принимаются под именами `declarations.json[l]`, `regulations.json[l]`
  из корня проекта (`--data` меняет каталог).
